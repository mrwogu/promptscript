Evaluating Prompts

View as Markdown

prs eval runs a prompt of your project over a dataset and checks every answer. A suite names the prompt, the dataset and the assertions. The run prints a report, and prs eval compare tells you if a later report is worse than an earlier one.

Read Application Prompts first. This page covers how to write suites and how to run them without a network in CI. The options and the exit codes are in the prs eval reference.

Offline by default

The default cache mode is replay. It answers every call from the files in .promptscript/eval-cache/ and never calls a provider, so it needs no key and no network. You record the answers once with a live model, commit them, and every later run, on your machine or in CI, replays the same bytes.

The example

The refund prompt from Support Refund Reply has a suite with five cases. The files, the recorded answers and the two reports are in the example folder. Everything below is read from there.

The suite checks four things in every answer. The output must fit the contract of the prompt, the decision must be the expected one, the reply must not say “we guarantee”, “I guarantee” or “guaranteed refund”, and a judge model must find the reply polite and within the policy. The regex is a cheap tripwire for these words only, a promise in other words is left to the judge.

The dataset is a JSONL file. One row has an id, the inputs of the prompt and the expected values. A row can also have tags.

The judge is a rubric, a prompt of the project like any other. This one is in the same project.prs as the prompt under test.

The answers were recorded with a live model once. The report of that run is reports/baseline.json. The second report, reports/regressed.json, is the same run with one answer changed in the cache, with only the decision field of late-return flipped to approve, so the run approves a refund it should deny. prs eval compare --fail-on-regression fails on the pair, and the CI of this repository checks that it does.

Suites

A suite is a file <name>.eval.yaml, .eval.yml or .eval.json under .promptscript/evals/. The name uses lowercase letters, digits and dashes. Unknown keys are errors, so a typo does not pass silently. Add the $schema line, as in the example, for editor help.

KeyWhat it does
promptThe prompt under test, as <project id>/<prompt id>
datasetA path relative to the suite file, or { path, allow, allowPii }, see below
assertions1 to 20 checks that every case must pass
modelsUp to 8 models to run the whole dataset on, each with optional params. Default: the model of the prompt
judgeSettings shared by the llm-judge assertions, such as model and runs
labelsA file of human verdicts for judge assertions
thresholdspassRate, maxCostUsd and other limits the run must meet

The prompts come from a fresh in-memory compile of the source. You do not need prs compile or a release first. To run the prompts an environment serves, use --label <env>, see the CLI reference.

Datasets

A dataset is JSONL, CSV or YAML, at most 1000 rows by default (--max-cases or eval.maxCases change that). Each row has an id, inputs that fit the input contract of the prompt, and optionally expected and tags. Values are never interpolated, so ${HOME} stays ${HOME}.

Before the run, the text of a row goes through five rules of prs validate: PS005 (blocked-patterns), PS010 (suspicious-urls), PS011 (authority-injection), PS012 (obfuscated-content) and PS014 (unicode-security). They are pattern based. The scan reads the string values in inputs (top level only, so a string nested in an object or a list is not read) and in expected (a plain string, or the string fields of an object and the strings in its lists). The same values go through detectors for email addresses, card numbers and IBANs. The IBAN check knows the length of the IBANs of the EU member states, the United Kingdom, Switzerland and Norway. An IBAN of another country is not found. A finding stops the run or warns, and it names the rule and the row, never the value. If a finding is expected, for example a test row with a made-up email, say so with the long form of dataset:

An allow entry needs a deterministic assertion in the suite (PS6213), so the row that you let through is still checked by something other than a model.

Know the limits. The scan reads one string at a time, so an instruction split over two inputs is not seen. The Unicode rule PS014 also flags zero-width characters, which some emoji sequences contain. Personal data in free text, such as names and postal addresses, is not detected. Read a dataset that came from production before you commit it.

To build a dataset from production samples, use prs eval import. It scrubs what the detectors find and writes a new file. See the reference.

Assertions

Put the deterministic ones first. They are cheap, they give the same result every time, and a model cannot talk them out of a failure.

KindPasses when
equalsthe target equals value, or the expected of the row
containsthe target contains all the values, or any of them with mode: any
regexthe pattern matches; negate: true flips it, as in no-guarantee above
json-schemathe response fits a JSON schema; the default is the output of the prompt
llm-judgemore than half of the judge runs say pass

field reads one property of the answer parsed as JSON. Without it the assertion reads the whole text. Regex patterns have a time limit, and an assertion that runs out fails the case. Later cases fail that assertion without running it again.

The judge

An llm-judge assertion sends the answer to a rubric. The rubric is a prompt of your project. Its output must be exactly a verdict of pass or fail, and a reason. The assertion makes 1, 3 or 5 runs, the default is 3, and passes when more than half say pass.

The text the judge reads was written by a model, or by a customer. Treat it as data:

  • Put response and case_inputs, and expected if the rubric declares it, in the user message, inside a fence made with boundary, as in the example. The boundary comes from a hash of the answer, so the answer cannot close its own fence. Text outside a fence is a warning, PS6216.
  • Keep all three out of the system message. That is an error, PS6212.
  • Say in the system message that the text in the tags is data.
  • Do not use the model under test as the judge, or you get a warning, PS6215.

Majority voting removes sampling noise. It does not remove an instruction hidden in the answer, so keep deterministic assertions next to the judge, as the suite does with decision-matches and no-guarantee.

The cache

record calls the provider for the cases that have no entry and stores the answers. replay reads them. An entry is looked up by a key over the bundle hash of the prompt, the inputs, the model, its parameters and the run number of the judge. Change any of those and the entry is a miss. In replay a miss is a case error, PS6402, and the message names the command that records again.

Things to know before you commit the cache:

  • The answers are text a model wrote about your inputs. Read them like you read the dataset.
  • A replay checks that an entry is well formed and fits its key. It cannot check that a model wrote it. Whoever can edit .promptscript/eval-cache/ can make a suite pass, so protect it as you protect the suite, for example with CODEOWNERS on .promptscript/evals/ and .promptscript/eval-cache/.
  • The digest in the report hashes the raw bytes of the entries. Stop Git from changing line endings with .promptscript/eval-cache/** -text in .gitattributes.
  • There is no pruning, and --cache record keeps old entries. To drop stale ones, delete the directory and record again.
  • To see if a run called a provider, read cache.mode and cache.live in the report. replayed alone does not tell.

Spending and keys

A live mode (record, refresh, off) needs --max-cost <usd>, else the run stops with PS6504. Before the first call the run adds up the worst case of every call that is not in the cache and stops with PS6503 if it is over the limit. During the run each call reserves its worst case first. The prices come from the model catalog and are an upper estimate. A model with no price is PS6501, and a project price lower than the built-in one is PS6505. Use --dry-run to see the plan first. It calls nothing and needs no key.

A key is read from an environment variable when the call is made, never from the config. Before the first live call stderr says sending <VAR> to <host>. The key goes only to api.anthropic.com, api.openai.com, the hosts you pass with --allow-host and, with --allow-local, loopback hosts, over http too. Host names are not resolved before the call, so a name that points to a private address after the check is a risk. Allow only hosts you control.

Reports and comparing

--format picks text, json, markdown or junit. With --out the report is also written to a file, and --report-dir writes one JSON file per suite. A JSON report has no timestamp, so two replays give the same bytes.

A case regressed when it passed in the baseline and does not pass now. A drop of the pass rate above --tolerance counts too. A report is a claim about one run, not a proof, and release gates do not read it. Replay it at the commit you gate to check it.

Only cases with the same suite, model and case id in both reports are compared. A case, model or suite that is in one report only is listed, but it is not a regression by itself. The pass rate of a model in both reports is still compared, so a smaller dataset can fail on --tolerance. A report that only lost cases can pass, even with --fail-on-regression.

In CI

Replay on every pull request, and run the live check on a schedule. The recipes are in the CI guide and in the drift check. Never give a provider key to code from a pull request, and never use --cache record, refresh or off there.
