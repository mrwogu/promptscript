Application Prompts

View as Markdown

PromptScript compiles instructions for coding agents. With syntax 1.6.0 it also compiles the prompts that an application sends to a model. You write each prompt as an entry of the @prompts block, and two opt-in targets turn the entries into files:

TargetWritesFor
bundleprompts/<key>.json and prompts/index.jsonApplications. One content-hashed file per prompt
prompt-textprompts/<key>.md and prompts/README.mdPeople. A Markdown preview of the system message

Neither target is part of an “all targets” default. Add them to targets when you want them. A program without @prompts entries writes nothing for either target. The coding agent targets skip the @prompts block and their output does not change.

Write a Prompt

A prompt is an entry of @prompts. It can reuse the blocks of the same program: the compose list names the blocks that become part of the system message.

The reference for every field is in the language reference. The file must declare syntax: "1.6.0" or later. Both targets refuse a lower version, a prerelease below it and a missing syntax, and prs validate warns about @prompts entries below it (an error with --strict).

The browser compiler used by the playground refuses a prompt target when it is created with environment variables, because it interpolates them while it parses and the bundle would differ from the one the CLI writes. Compile prompt targets without envVars.

The Bundle

The example above compiles to prompts/refund-reply.json:

FieldMeaning
$schemaSchema URL, always the first key. It is the version tag of the bundle. See Verify before use
id<@meta.id>/<key>
contentHashsha256- plus 64 lowercase hex characters
messagesOne or two messages, system first. Slots are left unrendered
inputsDeclared inputs. required is true for an input without a default
outputThe output contract as a JSON Schema subset. Every property is required and extra properties are not allowed
modelThe reference as written, plus the catalog profile, provider and API id it resolved to, and the parameters
governanceThe effective governance values of the prompt
provenanceWhere each message segment came from. Informational

The files follow the schemas schema/prompt-bundle-v1.json and schema/prompt-bundle-index-v1.json. They are written with two-space indentation and a final newline, and hold no timestamp, so the same source always gives the same bytes. Line endings in the source do not matter: every string in a bundle has \r\n and \r turned into \n.

prompts/index.json lists the bundles, sorted by id, with the contentHash of each.

Messages and composition

With compose, the system message is built from the listed blocks in a fixed order, whatever order you list them in: identity, context, knowledge, standards, restrictions, examples. The prompt’s own system text comes last. Segments are joined with one blank line and trailing spaces are trimmed. Without compose, the system message is the prompt’s own text.

  • identity is plain text. The other blocks sit under a heading such as ## Restrictions.
  • Properties of context and standards become - key: value bullets, and lists are indented one level.
  • restrictions become - bullets, and examples become an input and an output in fenced code.
  • Inside a block, its text, its list items and its properties are separate groups, in that order, divided by one blank line.
  • @header titles are ignored.

Every {{ in a composed block is escaped as \{{, so a composed block never carries a live slot. Only the prompt’s own system and user text can. A compose name must exist in the resolved program.

Runtime slots

{{input.name}} marks a value the application supplies when it calls the model. The name must be a declared input. The bundle keeps the slot as written. \{{ stands for two literal braces. The toolchain renders slots only inside prs eval, to call a model with a dataset row. An application fills them itself, through the runtime, and nothing in this guide describes how.

Governance

A prompt takes its own risk, owner, domain, dataClasses and reviewers, and falls back to the values in @meta. dataClasses is the union of both. Lists are sorted by UTF-16 code units and have no duplicates. Prompt policies in promptscript.yaml read these values: they can require fields, raise the risk from data classes, limit models and check the text.

Model

model.ref must name a model in the catalog, or a profile you declare under models.profiles in promptscript.yaml. A floating alias such as sonnet resolves to the release it points at when you compile. The resolved profile, provider and apiId are part of the content hash, so a catalog change cannot move the served model under a hash you pinned. prs validate warns about a floating alias with PS042.

Content Hash

contentHash is SHA-256 over the RFC 8785 canonical JSON of the bundle without contentHash and without provenance, written as sha256- plus the digest. $schema is inside the hash. A bundle of another schema version never shares a hash with a version 1 bundle.

Moving a source file, or moving identical text between layers, changes provenance and keeps the hash. A change to any message, input, output, model or governance value changes it. The conformance vectors pin the bytes.

Verify before use

A bundle is data from a file. A program that reads one should:

  • recompute contentHash and reject the bundle when it does not match;
  • validate the structure against the schema before it uses any field;
  • never fetch the URL in $schema, because it is a version tag and not a download link;
  • never deep-merge bundle JSON into defaults.

Previews

The prompt-text target writes the composed system message of each prompt to prompts/<key>.md, under a comment that holds the contentHash of the bundle. prompts/README.md lists the key, description and file of each preview. A prompt without a system message is skipped with warning PS4002.

A preview is for reading. It is not an approved artifact, and it still holds the slots and the escapes of the bundle. The CLI does not reformat these files and does not add a configured header to them.

Generated Files

Bundles and previews are generated output.

  • A bundle or index is recognised by its first key, "$schema" with a prompt bundle URL. A JSON file that only quotes the URL somewhere is never claimed.
  • When a prompt leaves the source, prs compile removes its files from the target directory. It removes a bundle only when the file parses, its contentHash verifies and its name is the one the target gives it, so a renamed copy or a hand-edited bundle stays. An index is removed only under the name the target gives it, index.json unless output names another file. It does not enter subdirectories.
  • The output directory belongs to the target. A verified bundle from another project that you save there is removed on the next compile.
  • A prompt key may not equal the file name of the output, as in key all with output: prompts/all.json. The compile fails and asks you to rename one of them.
  • A file at the path of a bundle that PromptScript did not generate is not overwritten without --force.
  • When the last prompt leaves the source, the target writes nothing and prs compile removes the files of the earlier compile by the same rule. A bundle you edited stays.

What PromptScript Does Not Do

Read this before you ship a bundle.

  • Input values. PromptScript never escapes, delimits or filters the values an application puts into a slot. Text a user supplies reaches the model as written. Treat it as untrusted.
  • Responses. Output schemas are not enforced. The application validates the response of the model. prs eval checks a response against the schema with a json-schema assertion, in tests only; the application still validates in production.
  • Secrecy. A system prompt is extractable by a user who interacts with the model. Composed text is public once shipped, so do not compose a block that holds anything you would not publish. The compile prints which blocks it composed for this reason.
  • Text blocks. A line that starts with # inside """ is prompt text, not a comment.
  • Environment variables. The bundle targets never interpolate ${VAR}. It stays text in the message. prs eval does not interpolate it in suites or datasets either.
  • Checks on authored text. The security rules of prs validate look at the text you wrote. They do not look at the values an application supplies at run time. prs eval scans the values of its dataset files with the same rules, which covers the test data and nothing else.
  • Online experiments. Traffic splitting, production sampling and live A/B tests are out of scope. prs eval runs a fixed dataset offline.
  • Provenance. It is informational. File names can reveal internal git hosts and project layout. A policy must evaluate the recompiled source, never the provenance of an artifact.
  • Personal data. owner and reviewers put names or addresses into production artifacts. Use team names when that matters.

Run prs validate --strict in CI, so a warning such as a slot in the system message (PS046) stops the build.
